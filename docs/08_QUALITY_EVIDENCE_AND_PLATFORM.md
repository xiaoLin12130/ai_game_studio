# 08｜质量、证据和微信平台门禁

## 质量门禁层级

1. 静态检查：格式、类型、lint、依赖、安全检查。
2. 自动化测试：单元、集成、状态机、业务契约和回归。
3. 引擎验证：Cocos 工程打开、脚本导入、资源引用、场景和构建。
4. 构建验证：目标平台产物存在、新鲜、配置正确、结构正确。
5. 微信开发者工具：导入本次 Build ID 产物并运行。
6. 真机验证：设备型号/系统/微信版本/测试步骤/截图和日志。
7. 人工验收：玩法、视觉、易用性和交付完整性。

未运行的层级必须标记 `NOT_RUN` 或 `BLOCKED`，不能折算成“整体通过”。

## 构建证据

每次构建生成不可变 `Build Manifest`，至少包括：

- Build ID；
- 源 Commit SHA；
- 项目/引擎版本；
- 构建命令、目标平台和配置；
- 开始/结束时间；
- 输出路径；
- 产物哈希和文件清单；
- 构建日志路径；
- 产物自证标记/本次特有标记；
- 验证环境和验证状态。

CLI 返回成功码不足以证明目标产物正确生成。必须确认新鲜度和来源，避免旧包被误认成本次构建。

## 微信平台专项

检查：胶囊/安全区、刘海屏、全面屏、iOS 音频自动播放限制、字体与中文折行、滚动、触摸、分享/广告/存档等平台能力是否真正接线、分包首屏 preload、包体限制、资源实际加载、生命周期、内存和性能。

微信平台配置/后台字段必须来自真实项目配置或平台界面，不能让模型编造官方字段或资质要求。

## 真机门禁

- 真机测试是正式验收门禁，不是可选备注。
- 没有真机条件时可以继续其他工作，但阶段状态为 `PARTIALLY_VERIFIED` / `BLOCKED`，不能宣称最终验收完成。
- Web Mock、浏览器预览和开发者工具不能代替真机。
- 真实截图和日志必须关联 Build ID、Commit SHA、时间戳、设备和环境。

## 测试脚本可信度

- 测试对象路径必须来自当前项目配置，不能硬编码到旧项目。
- 测试前断言项目/场景/节点/文件存在。
- FAIL 必须非零退出；禁止吞掉异常或把跳过写成通过。
- 输出可枚举用例、通过/失败/跳过数量和原始日志。
- 测试脚本本身需要最小自测。
- 夹具截图标记 `[FIXTURE]`；视觉量化与视觉模型交叉验证，避免单方判断。

## 最终质量状态

- `PASS`：所有要求门禁均完成且有证据。
- `PARTIALLY_VERIFIED`：部分门禁通过，仍有明确未验证项。
- `BLOCKED`：关键外部环境/平台条件缺失。
- `FAIL`：存在未解决的验收失败。

只有 `PASS` 才能标记为可交付；其他状态必须清晰说明风险。
